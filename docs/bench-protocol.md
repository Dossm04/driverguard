# Протокол стендовых испытаний DMS (ML-6, Приложение Г ТЗ)

Цель: измерить precision/recall по типам событий, задержку алерта, FPS и температуру в условиях
«день» и «ночь (ИК)» — KPI-1 (recall микросна ≥ 95 %), KPI-2 (precision всех алертов ≥ 90 %).
Стенд проводится **на CPU без Hailo** (ноутбук или Pi 5, тот же `device/dg`); после приезда
ускорителя протокол повторяется без изменений.

## Что нужно

- Устройство: `cd device && .venv/bin/python -m dg --source 0 --display --gps sim --no-sync` (или с sync — тогда
  события видны и в панели). Клавиша `c` — повторная калибровка перед каждым испытуемым.
- Испытуемые: ≥ 5 (цель 20, эксперимент A2), каждый — 20 сценариев × день/ночь × 3 повтора.
- Оператор с секундомером и протоколом CSV; часы устройства и ноутбука синхронизированы (NTP).
- Для ночных сценариев — ИК-подсветка 850 нм или затемнённая комната.

## Порядок

1. Сгенерировать протокол:
   ```bash
   cd ml && .venv/bin/python scripts/bench_protocol.py --subjects Иванов,Петров,Сидоров --out bench/protocol_2026-09-22.csv
   ```
   Колонки: `run_id, subject, condition, repeat, scenario_id, scenario, expected, started_at, stimulus_at, ended_at,
   observed, latency_ms, fps, temp_c, note`. Ожидаемые события уже проставлены (таблица ниже).
2. Для каждого прогона оператор записывает **started_at** (начало сценария), **stimulus_at** (момент,
   когда ожидается реакция: глаза закрыты 2 с → момент истечения 2 с; телефон у уха → через 2 с после
   поднесения) и **ended_at** (конец сценария). Формат ISO с поясом: `2026-09-22T10:15:30+05:00`.
   `fps`/`temp_c` — с плашки HUD. Между прогонами — пауза ≥ 35 с (cooldown событий 30 с).
3. Посчитать отчёт по событиям из SQLite устройства (или экспорта панели):
   ```bash
   .venv/bin/python scripts/bench_report.py bench/protocol_2026-09-22.csv --sqlite ../device/dg.sqlite --out ../docs/bench-report-2026-09-22.md
   ```
   Правило сопоставления: событие ожидаемого типа в окне `[started_at, ended_at + 5 с]` → TP, задержка =
   `ts − stimulus_at`; нет — FN; любое другое событие в окне → FP этого типа. Прогоны без времени
   пропускаются и считаются в «пропущено».
4. Приложить отчёт к спринту и внести пороги, которые пришлось поменять, в `docs/decisions.md`.

## Сценарии (Приложение Г)

| № | Сценарий | Ожидание |
|---|---|---|
| 1 | Глаза закрыты 2 с | microsleep |
| 2 | Глаза закрыты 1 с | нет события |
| 3 | Частые моргания 1 мин | нет события |
| 4 | Зевок ×3 за 3 мин | fatigue ×1 |
| 5 | Медленное опускание головы 3 с | head_nod |
| 6 | Взгляд вправо 10 с | distraction |
| 7 | Взгляд в зеркало 3 с | нет события |
| 8 | Телефон у уха 5 с | phone |
| 9 | Рука у уха без телефона | нет события |
| 10 | Телефон лежит на панели | нет события |
| 11 | Сигарета у лица 5 с | smoking |
| 12 | Ручка/карандаш у рта | нет события |
| 13 | Ремень пристёгнут, куртка тёмная | нет события |
| 14 | Без ремня 40 с | seatbelt (beta) |
| 15 | Очки прозрачные, сценарии 1–2 | как в 1–2 |
| 16 | Солнцезащитные очки, сценарий 5 | head_nod; без ложного microsleep |
| 17 | Головной убор с козырьком | детекция лица сохраняется |
| 18 | Лицо закрыто рукой 4 с | локальное предупреждение |
| 19 | Камера перекрыта 6 мин («движение» в симуляции) | camera_sabotage |
| 20 | Водитель вышел из кабины | предупреждение, нет ложных событий |

Сценарии 8–14 требуют детектора нарушений (`device/models/*.onnx`, `--detector on`); 6, 11, 14, 19
— скорость > 20 км/ч, поэтому на стенде используется `--gps sim` (симулятор даёт 60–90 км/ч).

## Что попадает в отчёт

По каждому типу и по каждому условию: TP / FP / FN, precision, recall, медиана задержки (мс);
сводно — KPI-1 и KPI-2; список несовпадений (ожидалось / наблюдалось) для разбора. Пример структуры —
`ml/dgml/bench.py::report_markdown`, проверен тестами `ml/tests/test_bench.py`.
