# DriverGuard: постоянный сервер из GitHub

Проверено по документации и API Railway 11 октября 2026 года. В аккаунте владельца создан проект `spirited-light`: Postgres, приватный Bucket Media, API и Web. Актуальный результат проверки развёртывания фиксируется отдельно; работоспособность на реальном телефоне проверяется по сценарию ниже.

Адреса текущего развёртывания:

- Панель: <https://web-production-c2a69.up.railway.app/login>.
- Вход водителя: <https://web-production-c2a69.up.railway.app/driver/login>.
- API для Android: <https://api-production-bd8b2.up.railway.app/api/v1>.

11 октября 2026: API/Web/Postgres запущены, готовность базы и файлового хранилища подтверждена. Проверены вход администратора, вход единственного демонстрационного водителя и закрытый доступ к списку водителей без авторизации. Созданы водитель `Demo A53 — test driver` и тестовый автомобиль `DG-DEMO-A53`; дорожные события не генерировались. API и Web подключены к `Dossm04/driverguard`, ветка `main`; исходники развёртываются на Railway после обновлений GitHub. Приватные данные входа находятся только у владельца в `.runtime/railway/access.json` и удобном `.runtime/railway/ACCESS_CLOUD.txt`, в Git они не публикуются.

Проверен облачный тестовый аудит №1 с семью изображениями `TEST — NOT A REAL VEHICLE INSPECTION`: повторная отправка UUID не создала дубль, фотография скачалась из приватного хранилища, отсутствие ИИ-провайдера корректно требует ручной проверки. Аудит отмечен `sent_to_repair` с пояснением, что это технический тест без допуска к движению. После нового развёртывания API из GitHub сохранились оба аккаунта, статус аудита и семь фотографий; повторный вход и скачивание фото прошли успешно. Временный `DG_BOOTSTRAP_ADMIN_PASSWORD` удалён из переменных Railway после создания аккаунта. Этот тест проверяет передачу и сохранение данных, а не точность распознавания на дороге.

GitHub хранит код и запускает проверки. FastAPI, PostgreSQL и Next.js должны работать на хостинге: GitHub Pages их не запускает. Здесь выбран один провайдер — Railway. После первого развёртывания ссылка останется прежней, пока сохраняются сервис и его домен; ноутбук для работы сервера не нужен.

## Что размещаем

| Имя в Railway | Назначение | Постоянное хранение |
|---|---|---|
| `Postgres` | Аккаунты, аудит, события, настройки | Том базы данных и резервные копии |
| `Media` | Приватные фото аудита и клипы | S3-совместимый Bucket |
| `API` | FastAPI, вход и приём событий | Через Postgres и Media |
| `Web` | Панель координатора и страницы водителя | Код из GitHub |

Фото и клипы используют один приватный бакет, но разные префиксы `checklists/` и `clips/`. Для просмотра выдаются временные подписанные ссылки. Сырые файлы не хранятся на временном диске контейнера.

## Цена и доступ — до создания ресурсов

- Вход: <https://railway.com/login>, затем подключить GitHub-аккаунт владельца `Dossm04/driverguard`.
- Hobby стоит минимум **$5 в месяц**, включая $5 ресурсов. Превышение оплачивается по использованию. Это **не обещание**, что весь наш стек будет стоить ровно $5.
- Пробный кредит, если он доступен конкретному аккаунту, ограничен; постоянную бесплатную работу на нём не обещаем.
- В текущем аккаунте перед запуском подтверждены Trial и $5 кредита на срок до 30 дней. Платный тариф и платёжные данные при настройке не подключались. Проверять оставшийся кредит перед защитой: израсходованный кредит или завершение Trial могут остановить доступность.
- После входа открыть Workspace → Usage: посмотреть Trial/план, остаток кредита и условия оплаты. Перед переходом на платный тариф владелец подтверждает бюджет.
- Настроить предупреждение и **Compute Hard Limit** на согласованный бюджет. При достижении лимита сервер остановится; эту границу нужно учитывать перед защитой. Порог нельзя выбирать молча за владельца.
- Для первого теста не включать Railway Agent: для нашего приложения он не нужен и оплачивается отдельно.

Источники: [тарифы](https://docs.railway.com/pricing/plans), [контроль расходов](https://docs.railway.com/pricing/cost-control), [хранение файлов](https://docs.railway.com/storage-buckets/billing).

## Подготовка GitHub

1. Проверенные файлы из `infra/railway/` должны находиться в ветке репозитория, выбранной для развёртывания. Локальный файл сам по себе Railway не увидит.
2. Не загружать `.env`, приватные ключи, файлы доступов, локальную базу или Android-keystore. Примеры `*.env.example` содержат только названия переменных и заглушки.
3. Railway GitHub App должен видеть **только нужный репозиторий**. Если потребуется новая выдача доступа, владелец выполняет её в интерфейсе GitHub.
4. В репозитории уже есть `.github/workflows/ci.yml`. После зелёных проверок можно включить `Wait for CI` в обоих сервисах Railway. Дополнительный токен GitHub Actions для обычного автодеплоя не нужен.

## Первое развёртывание

Работать в новом облачном проекте. Локальная Docker-база и существующие пароли на ноутбуке не меняются.

1. New Project → Empty Project → имя `DriverGuard`.
2. Добавить PostgreSQL и назвать сервис ровно `Postgres`. Проверить, что подключён постоянный том. Не открывать PostgreSQL в интернет; API использует внутренний `DATABASE_URL`.
3. Добавить Bucket и назвать его `Media`. Выбрать регион, доступный и удобный для проекта. Реальное S3-имя содержит суффикс: использовать переменную `Media.BUCKET`, а не видимое имя `Media`.
4. Добавить два пустых сервиса: `API` и `Web`. Подключить к обоим репозиторий `Dossm04/driverguard` и проверенную ветку. Оставить Root Directory пустым: специальные Dockerfile используют корень репозитория как контекст.
5. В `API` указать Dockerfile Path: `infra/railway/backend.Dockerfile`, healthcheck `/api/v1/health/ready`; в `Web` — `infra/railway/web.Dockerfile`, healthcheck `/login`. Тайм-аут проверки 180 секунд, restart policy On Failure, 5 попыток. Railway Config File оставлять пустым: новые сервисы больше не принимают устаревший `railway.json`. Файлы `backend.service.json` и `web.service.json` содержат те же настройки для поддерживаемого API. Их можно применить через уже авторизованный официальный CLI: `python infra/railway/configure_service.py --service-id <ID> --environment-id <ID> --kind backend` (для Web — `--kind web`). Это не создаёт ресурсы и не записывает секреты.
6. В Networking → Generate Domain создать HTTPS-домен `API`, target port **8000**, и домен `Web`, target port **3000**. Сохранить адреса; это будущие постоянные ссылки. Если интерфейс предлагает развёртывание раньше настройки — остановиться на настройке переменных, не считать такой запуск готовым.
7. В `API → Variables → Raw Editor` перенести `infra/railway/backend.env.example`. Подставить домен Web в `CORS_ORIGINS`; ссылки `${{Postgres.…}}` и `${{Media.…}}` Railway разрешит из этого же проекта. Убедиться, что все ссылки распознаны.
8. Задать `JWT_SECRET`: случайная строка минимум 32 байта. Задать уникальные `DG_BOOTSTRAP_ADMIN_EMAIL` и `DG_BOOTSTRAP_ADMIN_PASSWORD` (минимум 12 символов). Значения вводятся в приватные переменные Railway, не в репозиторий/чат. Использовать генератор паролей владельца.
9. Для нового Railway Bucket оставить `MINIO_VIRTUAL_HOST_STYLE=true`. Если Credentials явно показывает старый path-style endpoint — выставить `false`. Регион и endpoint брать из Credentials/ссылок переменных, не угадывать.
10. В `Web → Variables` перенести `infra/railway/web.env.example`, в трёх адресах заменить домен на созданный домен API. `NEXT_PUBLIC_*` встраиваются при сборке: после изменения нужна новая сборка.
11. У обоих сервисов оставить одну реплику; Serverless/сон выключить для демонстрации с постоянной доступностью. Стартовые RAM-лимиты выбрать после пробного запуска и просмотра Metrics, не обещать производительность без замера.
12. Развернуть `API` после готовности Postgres и Media, дождаться успешного `/api/v1/health/ready`. Затем развернуть `Web` и проверить `/login`.

Старт API переводит стандартный PostgreSQL URL Railway в формат установленного драйвера `psycopg`, применяет миграции и **только на пустой базе** создаёт первого администратора и депо. Он не создаёт демонстрационные аварии и не сбрасывает существующие учётные записи. `SEED=never` и `DEMO_MODE=false` обязательны для этой конфигурации.

После успешного первого входа удалить из Railway переменную `DG_BOOTSTRAP_ADMIN_PASSWORD` и развернуть API повторно: существующий аккаунт сохранится, а пароль больше не будет храниться в конфигурации. Сброс пароля выполняется штатным отдельным процессом, не повторным seed.

## Учётная запись водителя и аудит

1. Открыть `https://<WEB-домен>/login`, войти первым администратором.
2. В разделе «Водители» создать водителя с номером телефона и PIN. PIN должен быть задан: запись водителя без PIN не даёт возможность входа.
3. Добавить/назначить автомобиль. В настройках проверить состав предрейсового чек-листа. Использовать только собственные тестовые сведения и фотографии.
4. В Android-приложении задать API `https://<API-домен>/api/v1`, затем войти тем же номером и PIN. Не использовать `localhost`: на телефоне это сам телефон.
5. Для страницы аудита в браузере использовать `https://<WEB-домен>/driver/login`. Если APK открывает этот раздел, он должен использовать **Web-домен**, а не API-домен.
6. Выполнить один аудит с фотографиями и проверить его в панели. Просмотр миниатюр и загрузка оригинала должны работать; HTTP 200 у API сам по себе этого не доказывает.

Обработка фото внешней ИИ-моделью — отдельная настройка сервера. Без ключей провайдера или при `AI_PROVIDER=mock` обновлённый backend сохраняет статус недоступности ИИ и требует ручной проверки; он не выдаёт ложный результат «всё исправно». Подключить разрешённый провайдер в приватных Variables, проверить статус провайдера и получить настоящий результат; не включать отправку личных фото внешнему провайдеру без согласованного назначения и доступа.

## Проверка после развёртывания

В корне репозитория:

```text
python infra/railway/check_deployment.py --api https://<API-домен> --web https://<WEB-домен>
```

Проверка только читает: API отвечает, база и файлы доступны, справочник водителей защищён входом, обе страницы входа открываются. Она не создаёт событий и не выводит пароли.

Полный приёмочный сценарий:

1. Войти водителем на A53 при наличии сети.
2. На неподвижном месте запустить мониторинг, отключить интернет, вызвать и сохранить тестовое событие; записать его время/ID.
3. Включить интернет, оставить приложение открытым и выполнить синхронизацию. Проверить именно это время/ID в панели под правильным водителем.
4. Повторить синхронизацию: дубль события появляться не должен.
5. Отправить аудит с собственными тестовыми фото, открыть его в панели и проверить все вложения.
6. Перезапустить API и Web (не удалять сервисы): аккаунт, событие и фотографии должны сохраниться.
7. Отключить ноутбук от сети: с A53 через мобильный интернет повторить вход и чтение журнала. Это проверяет независимость сервера от ноутбука.
8. Только после этого кодировать Web-адрес страницы входа/материалов в основной QR. Не включать пароль или администраторский токен в QR.

Если шаг не проверен, отмечать его как «не проверено», а не «готово».

## Сохранность данных и обновления

- Подключить резервные копии тома Postgres в Railway и проверить восстановление в отдельную базу. Локальный `infra/backup.py` предназначен для Docker на ноутбуке и не является резервным копированием Railway.
- Не удалять Postgres/Media и не менять проект ради обновления. Обычный deploy меняет приложение, а данные остаются в выделенных хранилищах.
- Текущее облачное хранилище не настраивает автоматическое удаление файлов по сроку. Локальное удаление клипов в Android не удаляет копии в облаке. Политику хранения сервера подключают отдельно после согласования срока, без удаления нужных материалов.
- Изменение JWT_SECRET завершит действующие сессии. Изменение bootstrap-пароля не меняет пароль уже созданного пользователя.
- Остановить оплату/исчерпать лимит означает потерять доступность. Перед защитой проверить Usage, здоровье сервисов и резервную видеодемонстрацию.

## Когда что-то не работает

| Симптом | Что проверить |
|---|---|
| 502 или Application failed to respond | PORT и target port: API 8000, Web 3000; логи контейнера |
| Readiness 503, `db: error` | Postgres запущен; внутренний DATABASE_URL распознан; миграции прошли |
| Readiness 503, `storage: error` | Media.BUCKET/REGION/ENDPOINT и virtual-hosted стиль; ключ не просрочен |
| Вход работает в APK, браузер блокирует API | Точный HTTPS Web-origin в CORS_ORIGINS без слеша в конце |
| В браузере запросы идут на localhost | NEXT_PUBLIC_API_URL/WS_URL были неверны при сборке; пересобрать Web |
| Пароль не подходит после переноса | Облако — новая база; использовать облачный bootstrap-аккаунт, не ожидать переноса локальных учёток |
| Аудит есть, фото не открываются | Срок подписанной ссылки, доступ к Media; для прямых браузерных PUT проверить CORS бакета |
| Нет события с телефона | Совпадают аккаунт и API, сеть восстановлена, очередь не пуста, вход действителен; посмотреть ответ синхронизации |
