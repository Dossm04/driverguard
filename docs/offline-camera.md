# Камера без интернета

Обновление от 5 октября 2026. Требования: APP-8, store-and-forward и KPI-5.

## На телефоне

1. Пока есть интернет, откройте постоянную HTTPS-ссылку в Safari и войдите как водитель.
2. Откройте «Камера», прокрутите до «Подготовить офлайн» и нажмите кнопку.
3. Дождитесь «Камера подготовлена для офлайн». Основной комплект занимает около 46 МБ;
   опубликованная модель предметов увеличит объём. Файлы проверяются по контрольным суммам.
4. Включите авиарежим, выключите Wi-Fi, перезагрузите этот экран и нажмите «Включить камеру».
5. Для проверки микросна на неподвижном месте закройте глаза примерно на 2 секунды после
   калибровки. Проверьте предупреждение и звук. Это ручная проверка, её результат нужно записать.
6. Счётчик «Сохранено на телефоне» показывает ещё не отправленные события.
7. Снова включите интернет. Оставьте приложение открытым под той же учётной записью;
   очередь автоматически отправится. Проверьте событие в панели координатора.

Предупреждения обрабатываются на телефоне. Для отправки событий, первоначального входа,
панели координатора и доступа по QR нужен работающий сервер и интернет. Камера работает
при открытом экране приложения; iOS останавливает её в фоне. Не очищайте данные Safari до
синхронизации. После очистки хранилища подготовка нужна снова.

## Что сохраняется

- IndexedDB `dg-camera-events`: UUID события, время, тип, координаты при разрешённом GPS,
  источник детекции и идентификатор текущего водителя. Видеопоток здесь не сохраняется.
- События отправляются только из очереди текущего водителя. Повтор одного UUID не создаёт
  второе событие: сервер использует уникальный индекс PostgreSQL.
- Сетевые ошибки, 401/403/408/429 и ошибки сервера сохраняют очередь. Ошибочная запись
  изолируется от остальных, остаётся на устройстве и доступна для скачивания JSON.
- При запрете или переполнении хранилища появляется предупреждение: неподтверждённые записи
  временно остаются в памяти открытой вкладки. Это не считается надёжным сохранением.
- Service worker не кэширует API, токены и ответы входа. Подготовленный комплект включает
  HTML камеры, статические и динамические модули, локальные модели лица/рук и WASM.
- После установки новой модели предметов нажмите «Обновить офлайн-файлы» на каждом телефоне.
  Прерванное обновление сохраняет предыдущий полный комплект.

## Телефон, сигарета и ремень

В проекте подготовлен загрузчик модели из `training/install_candidate.py`.
Для событий модели сохраняются `detector=object_model`, версия и SHA-256. Ремень без этих
полей отвергается. Метаданные описывают результат клиента; они не являются серверной
независимой проверкой точности распознавания.

До импорта обученных весов работает явно обозначенный режим жестов; ремень не оценивается.
Обучение требует доступной GPU-сессии либо готового проверяемого архива результата.

## Проверки обновления

На тестовом браузере Microsoft Edge/Chromium под Windows выполнены:

- подготовка полного комплекта файлов;
- отключение сети и перезагрузка страницы;
- повторная загрузка настоящего MediaPipe/WASM с искусственной веб-камерой;
- сохранение тестового события в IndexedDB и перезагрузка;
- восстановление сети, отправка исходного UUID и очистка очереди.

Это проверка программного сценария. Она не заменяет проверку распознавания на реальных
водителях и тест Safari на физическом iPhone. Подготовка доступного кандидата также не
доказывает качество телефона/курения/ремня без независимых видео и разметки.

Юнит-тесты: `cd web && npm run test:unit`. Проверки backend камеры/авторизации запускаются
через pytest с отдельной БД `driverguard_test_<PID>`; использовать рабочую базу как тестовую нельзя.

Известное предупреждение аудита зависимостей: цепочка `braces` в инструментах Tailwind/glob.
Аудит npm на момент проверки не предлагает совместимого исправления. В эту доработку
переход на другую основную версию Tailwind не включён; перед постоянной публичной
эксплуатацией нужен отдельный пересмотр зависимостей и режима развёртывания.
