## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Наименование
Аппаратно-программный комплекс «DriverGuard» — Edge-AI система мониторинга состояния водителя, контроля нарушений и предрейсового допуска для автопарков грузового транспорта (далее — Система, Комплекс).

### 1.2. Состав Комплекса
1. **Устройство** — бортовой модуль с ИК-камерой, вычислителем и GPS, устанавливаемый в кабину.
2. **Облачная платформа (Бэкенд)** — приём и хранение событий, скоринг, ИИ-проверка чек-листов, API.
3. **Панель координатора (Web)** — дашборд, карта, события, лидерборд, водители, чек-листы, отчёты, настройки.
4. **Приложение водителя (PWA)** — смена, чек-лист, личный скоринг, SOS, микрообучение.
5. **Telegram-бот** — оперативные алерты координатору.
6. **ML-контур** — датасет, обучение, оценка и выпуск моделей на устройство.

### 1.3. Сроки
Софт MVP с демо-данными — до 11.09.2026 (спринт 4). Софт + устройство на стенде — до 25.09.2026 (спринт 5). Пилотная установка на 1 автомобиль партнёра — до 09.10.2026 (спринт 6). Приёмка MVP и защита — 16.10.2026.

### 1.4. Термины и сокращения
| Термин | Значение |
|---|---|
| DMS | Driver Monitoring System — мониторинг состояния водителя по видео |
| Edge AI | Обработка нейросетями на самом устройстве, без облака |
| EAR / MAR | Eye/Mouth Aspect Ratio — геометрические признаки закрытия глаз / открытия рта |
| PERCLOS | Доля времени с закрытыми глазами в скользящем окне (стандартный индикатор усталости) |
| Микросон | Эпизод непроизвольного закрытия глаз ≥1,5 с во время движения |
| Событие (Event) | Зафиксированный Системой факт (нарушение или признак усталости) с меткой времени, координатами, скоростью, уверенностью |
| Driver Score | Интегральный балл безопасности водителя 0–100 |
| Streak (серия) | Число подряд идущих дней без критических событий |
| Клип | Видеофрагмент 15 с (10 с до + 5 с после события) |
| Координатор | Сотрудник, выпускающий машины на линию и реагирующий на алерты |
| Хелпер | Сопровождающий в кабине (экспедитор), не является пользователем Системы в MVP |
| Store-and-forward | Режим накопления данных офлайн с автоматической отправкой при появлении сети |
| HEF | Скомпилированная модель для ускорителя Hailo |
| ИК | Инфракрасная подсветка/съёмка (850 нм в MVP) |

## 2. НАЗНАЧЕНИЕ И ЦЕЛИ СОЗДАНИЯ СИСТЕМЫ

### 2.1. Назначение
Система предназначена для предотвращения ДТП, связанных с усталостью и отвлечением водителя, путём локальной (на устройстве) детекции опасных состояний с немедленным предупреждением водителя, а также для автоматизации предрейсового допуска и объективной оценки водителей.

### 2.2. Цели
| Цель | Показатель |
|---|---|
| Снижение аварийности по вине усталости | Инциденты и near-miss на 1 млн км: −40…60% за 6 месяцев внедрения (целевой ориентир из Lean Canvas; в MVP — сбор базовой статистики) |
| Своевременное пробуждение водителя | Алерт на устройстве ≤1 с от момента детекции; реакция водителя <2 с у ≥90% испытуемых на стенде |
| Доверие водителей | Precision алертов ≥90%; ≤1 ложный алерт за 8-часовую смену |
| Замена формального осмотра | Чек-лист с ИИ-проверкой ≤60 с на водителя; доля заполненных чек-листов ≥95% рейсов |
| Управляемость для координатора | Время от события до уведомления координатора ≤10 с при наличии сети; отчёт по периоду — один клик |

### 2.3. Целевые показатели качества MVP (KPI приёмки)
| ID | Показатель | Значение |
|---|---|---|
| KPI-1 | Recall микросна на стенде (день и ночь/ИК) | ≥95% (стенд, 20 добровольцев — эксперимент A2) |
| KPI-2 | Precision всех алертов на стенде | ≥90% |
| KPI-3 | Ложные алерты в полевом тесте | ≤1 за 8 ч смены |
| KPI-4 | Задержка локального алерта | ≤1 с |
| KPI-5 | Доставка накопленных офлайн-событий после появления сети | ≤60 с |
| KPI-6 | Аптайм устройства в пилоте | ≥98% времени рейса |
| KPI-7 | FPS DMS-пайплайна на устройстве | ≥10 (CPU), ≥15 (с ускорителем) |
| KPI-8 | Загрузка страниц панели координатора | ≤2 с (p95) при 50 машинах |
| KPI-9 | Ответ API | ≤300 мс (p95) |
| KPI-10 | ИИ-проверка чек-листа | ≤30 с на комплект из 7 фото |

### 2.4. Границы MVP
**Входит:** всё, что помечено MUST в разделе 5; одно устройство; один пилотный автопарк; русскоязычный интерфейс.
**Не входит (следующие версии):** серийный корпус с диапазоном −40…+60 °C; комплаенс-движок рабочего времени (ТК РК/ЕСТР) с готовыми IVMS-отчётами; подписки и биллинг; интеграция со страховыми; оценка доставки получателем; мультиязычность (KZ) — только заготовка; распознавание водителя по лицу для авто-привязки; OTA-обновление прошивки (в MVP — конфигурации и модели вручную/по сети).

## 3. ХАРАКТЕРИСТИКА ОБЪЕКТА АВТОМАТИЗАЦИИ

### 3.1. Описание
Автопарк грузового транспорта дистрибуции: региональные рейсы с плечом 500–2000 км, включая ночные; внутригородская доставка. Утренний выпуск машин координатором; предрейсовый осмотр по бумажному/формальному чек-листу; физическая проверка координаторами 3–4 раза в неделю, не каждой машины. Связь на трассах прерывистая. Питание в кабине 12/24 В. Летом температура на торпедо может превышать 60 °C, зимой ниже −30 °C (в MVP устройство эксплуатируется в диапазоне 0…+50 °C, см. 6.5).

### 3.2. Роли пользователей
| Роль | Задачи в Системе | Устройство |
|---|---|---|
| **Водитель** | Начать/завершить рейс, перерыв с причиной, чек-лист с фото, получать алерты, видеть свой Score и место в лидерборде, SOS, микрообучение | Устройство в кабине + PWA на личном телефоне |
| **Координатор транспорта** | Живая карта, лента событий, подтверждение/отклонение событий, звонок водителю, согласование чек-листов, назначение обучения, лидерборд | Панель координатора (браузер) + Telegram |
| **Администратор** | Пользователи, устройства, веса скоринга, пороги, уведомления, экспорт | Панель координатора |
| **Руководитель (логист / менеджер по логистике)** | Отчёты по периоду, Score парка, динамика, экспорт | Панель координатора (только чтение) |

### 3.3. Пользовательские сценарии (User Stories)
| ID | Сценарий | Критерий приёмки |
|---|---|---|
| US-1 | Как водитель, я хочу, чтобы устройство разбудило меня, если я засыпаю, — до того, как об этом узнает кто-то ещё | Каскад сигналов срабатывает локально ≤1 с; уведомление координатору уходит только при критическом событии |
| US-2 | Как водитель, я хочу заполнить чек-лист за минуту прямо у машины | 7 фото с камеры телефона без галереи, вердикт ИИ ≤30 с |
| US-3 | Как водитель, я хочу видеть свой Score и серию и понимать, за что баллы сняты | Экран «Мой Score» с событиями и советами; ложные срабатывания оспариваются через координатора |
| US-4 | Как водитель, при поломке или ДТП я хочу одной кнопкой вызвать координатора с координатами | SOS с удержанием 3 с → координатор получает сообщение с картой ≤10 с |
| US-5 | Как координатор, я хочу утром видеть, кто допущен к выезду, а у кого замечания | Страница Чек-листы с вердиктами, кнопки согласования |
| US-6 | Как координатор, я хочу мгновенно узнавать о микросне на линии и позвонить водителю | Telegram-алерт с кнопкой «Позвонить», карта с красным маркером |
| US-7 | Как координатор, я хочу пометить ложное срабатывание, чтобы водителя не наказали зря | Review → возврат баллов, кадр в очередь дообучения |
| US-8 | Как руководитель, я хочу еженедельный отчёт по парку в один клик | Отчёт PDF/CSV с событиями, Score, км |
| US-9 | Как администратор, я хочу менять веса и пороги без программиста | Настройки с предпросмотром пересчёта |
| US-10 | Как команда, мы хотим показать полный цикл на демо без реальной машины | Режим симуляции устройства + seed-данные |

### 3.4. Условия эксплуатации устройства (MVP)
Кабина грузового автомобиля; монтаж на стойке A / у зеркала; питание от бортсети 12/24 В через преобразователь; вибрация; отсутствие сети до нескольких часов; ночь без внешнего освещения; водитель в очках, солнцезащитных очках, головном уборе.

## 4. ТРЕБОВАНИЯ К СИСТЕМЕ В ЦЕЛОМ

### 4.1. Структура и архитектура
```
 КАБИНА                              ОБЛАКО                               ПОЛЬЗОВАТЕЛИ
 ┌──────────────────────┐   HTTPS    ┌──────────────────────┐   HTTPS/WS  ┌───────────────┐
 │ Устройство           │──events──▶ │ Бэкенд (FastAPI)     │◀──────────▶ │ Панель        │
 │ ИК-камера → DMS      │──clips───▶ │ PostgreSQL · MinIO   │             │ координатора  │
 │ Hailo → нарушения    │◀─config──  │ Скоринг · Чек-лист ИИ│──alerts───▶ │ Telegram-бот  │
 │ GPS/OBD · SQLite     │            │ WebSocket /ws/live   │◀──────────▶ │ PWA водителя  │
 │ Алерты · sync-агент  │            └──────────┬───────────┘             └───────────────┘
 └──────────────────────┘                       │ retrain_queue
                                       ┌────────▼─────────┐
                                       │ ML-контур        │
                                       │ датасет→YOLO→HEF │
                                       └──────────────────┘
```
| ID | Требование | Приоритет |
|---|---|---|
| SYS-1 | Весь инференс DMS и детекции нарушений выполняется на устройстве; в облако передаются события (JSON) и клипы только по событию. Непрерывный видеопоток не передаётся и не хранится | MUST |
| SYS-2 | Подсистемы взаимодействуют только через документированный REST/WebSocket API (docs/api.md, OpenAPI) | MUST |
| SYS-3 | Бэкенд stateless, масштабируется горизонтально; состояние — в PostgreSQL и MinIO | SHOULD |
| SYS-4 | Все конфигурируемые параметры (пороги, веса, лимиты) хранятся в базе и редактируются через Настройки; устройство получает их при синхронизации | MUST |

### 4.2. Режимы функционирования
| Режим | Описание |
|---|---|
| **Онлайн** | Устройство отправляет события в течение ≤5 с после фиксации; позиции — каждые 10 с (по WS/пакетно) |
| **Офлайн (store-and-forward)** | Нет сети: детекция и алерты работают полностью; события и клипы копятся в локальной SQLite и файловой очереди; при появлении сети — отправка батчами с идемпотентностью по UUID; порядок — сначала события, затем клипы |
| **Деградированный** | Перегрев/ошибка ускорителя → детекция нарушений отключается, DMS продолжает работать на CPU; событие «self_diag» уходит на бэкенд |
| **Симуляция / демо** | Устройство без камеры генерирует правдоподобные события и движение по маршруту; бэкенд с seed-данными; переключается флагом, помечается `is_demo` |
| **Калибровка** | Первые 3 с после обнаружения лица в начале рейса — персональная базовая линия EAR и наклона головы |

### 4.3. Надёжность
| ID | Требование | Приоритет |
|---|---|---|
| REL-1 | Автозапуск всех сервисов устройства после подачи питания ≤40 с; перезапуск упавшего процесса (systemd Restart=always) | MUST |
| REL-2 | Устройство переживает внезапное отключение питания без потери уже записанных событий (журналируемая ФС, fsync после каждой записи события; клипы пишутся во временный файл и переименовываются по завершении) | MUST |
| REL-3 | Повторная отправка события не создаёт дубликата (UUID генерируется на устройстве) | MUST |
| REL-4 | Локальное хранилище: кольцевое удаление самых старых отправленных клипов при заполнении >80% диска; неотправленные не удаляются 7 дней | MUST |
| REL-5 | Мониторинг: температура SoC, FPS, свободное место, статус GPS/сети — раз в 60 с в лог и раз в 10 мин на бэкенд (heartbeat) | MUST |
| REL-6 | Резервное копирование БД бэкенда ежедневно, хранение 14 дней | SHOULD |
| REL-7 | «Золотой образ» microSD устройства с восстановлением за ≤30 мин | MUST |

### 4.6. Производительность и масштабирование
Устройство: DMS ≥10 FPS на CPU, ≥15 FPS общий пайплайн с ускорителем при 640×480; задержка алерта ≤1 с. Бэкенд MVP: до 50 устройств и 20 одновременных пользователей панели на VPS 2 vCPU / 4 GB; API p95 ≤300 мс; WS-обновления позиций ≤2 с. Хранилище: расчёт 15 клипов/сутки/машина × ~3 МБ.

### 4.7. Эксплуатация и сопровождение
Обновление конфигурации и модели на устройстве — по сети (скачивание при heartbeat, применение при остановке машины), с откатом на предыдущую версию при ошибке запуска. Логи устройства — ротация 7 дней. Панель показывает версию ПО и модели каждого устройства.

## 5. ТРЕБОВАНИЯ К ФУНКЦИЯМ

### 5.1. Подсистема «Устройство»
| ID | Функция | Описание | Приоритет |
|---|---|---|---|
| DEV-1 | Захват видео | ИК-камера (UVC), 640×480 @ 30 FPS, автоматическая работа в темноте с подсветкой 850 нм | MUST |
| DEV-2 | Детекция лица и ключевых точек | MediaPipe Face Landmarker: 478 точек + blendshapes; одно лицо (ближайшее к центру) | MUST |
| DEV-3 | Микросон | Глаза закрыты (blendshape eyeBlink ≥0.5, подтверждение EAR) непрерывно ≥1,5 с → событие `microsleep` (critical). Настраиваемый порог 1,0–3,0 с | MUST |
| DEV-4 | Моргания и PERCLOS | Подсчёт морганий (60–500 мс) в минуту; PERCLOS в окне 60 с; PERCLOS ≥20% → событие `fatigue` (warning), не чаще 1 раза в 30 с | MUST |

## 6. ТРЕБОВАНИЯ К ВИДАМ ОБЕСПЕЧЕНИЯ

### 6.1. Математическое обеспечение
**6.1.1. EAR** = (‖p2−p6‖ + ‖p3−p5‖) / (2‖p1−p4‖) по точкам контура глаза; порог закрытия ≈0.20 (используется как контроль к blendshape eyeBlink).
**6.1.2. PERCLOS** = доля кадров с закрытыми глазами в скользящем окне 60 с; начало расчёта после 15 с данных.
**6.1.3. Микросон** — непрерывное закрытие ≥ T_ms (по умолчанию 1500 мс); моргание — 60–500 мс, в микросон не засчитывается.
**6.1.4. Наклон/поворот головы** — по 3D-точкам лица (лоб–подбородок для pitch, скулы для yaw) относительно персональной базы калибровки.
**6.1.5. Driver Score** за период D дней:
`Score = clamp(40, 100, round(100 − Σ(w_i × m_i) × 7/D × 0.8 + min(streak, 10)))`,
где w_i — вес события (Приложение А), m_i — модификатор скорости (phone/microsleep при >60 км/ч ×1.5; phone при <5 км/ч ×0.3), учитываются события со статусом `new` или `confirmed`; `false_positive` исключаются. Зоны: ≥85 зелёная, 70–84 жёлтая, <70 красная.
**6.1.6. Streak** — число подряд идущих календарных дней с рейсами без critical-событий; бейджи: 7 дней «Неделя без риска», 30 дней «Железная выдержка», 10 ночных рейсов без событий «Ночной страж».
**6.1.7. Вердикт чек-листа** — «не допущен», если хотя бы один критический пункт (фары, шины, тормоза/утечки) в статусе неисправности с confidence ≥0.8; «требует внимания» — любые некритические замечания; иначе «допущен». Confidence <0.6 → пункт помечается «не видно», требуется повторное фото.

## 9. ПОРЯДОК КОНТРОЛЯ И ПРИЁМКИ

### 9.1. Виды испытаний
1. **Модульные** — автотесты бэкенда (скоринг, идемпотентность, review, парсер вердикта), устройства (машина состояний), фронтенда (Playwright smoke по всем страницам в обеих темах). Порог: тесты зелёные, покрытие критической логики скоринга 100%.
2. **Интеграционные** — `make demo` с нуля ≤5 мин; сценарий офлайн→онлайн; чек-лист от PWA до панели; SOS до Telegram.
3. **Стендовые** — протокол Приложения Г: 20 сценариев × 3 повтора × день/ночь, ≥5 испытуемых (цель — 20 по эксперименту A2); расчёт precision/recall по типам.
4. **Полевые** — ≥3 рейса на автомобиле партнёра; подсчёт ложных алертов на смену, аптайм, доля заполненных чек-листов, реакция водителя (интервью).
5. **Приёмочные** — проверка по чек-листу 9.2 комиссией (команда + ментор + представитель партнёра).

### 9.2. Критерии приёмки MVP
| № | Критерий | Метод проверки |
|---|---|---|
| П-1 | Все требования MUST разделов 4–5 реализованы | Демонстрация + матрица трассировки |
| П-2 | KPI-1, KPI-2, KPI-4, KPI-7 выполнены на стенде | Протокол Приложения Г |
| П-3 | KPI-5: события, накопленные без сети ≥30 мин, доставлены ≤60 с после появления сети без дубликатов | Тест с отключением сети |
| П-4 | KPI-8, KPI-9 при seed-данных (50 машин, 5000 событий) | Замер в браузере / нагрузочный скрипт |
| П-5 | Обе темы на всех 8 страницах панели и 5 экранах PWA без визуальных дефектов | Скриншоты Playwright |
